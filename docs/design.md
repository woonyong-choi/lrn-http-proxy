# 설계 — 무엇을 고르고 무엇을 버렸는가

이 문서는 `webproxy-lab/proxy.c` 의 결정 네 개를 기록한다. 각 항목은 고른 것,
버린 대안 두 개와 버린 이유, 그리고 그 결정이 깨졌을 때 무엇이 잡아내는지를
적는다. 숫자는 모두 [`bench.md`](bench.md)(재현: `make bench`)에서 왔다.

## 0. 이 프록시가 지켜야 하는 불변식

| # | 불변식 | 지키는 테스트 |
|---|---|---|
| I1 | 캐시가 돌려준 바이트는 원본이 보낸 바이트와 동일하다 | `test_cached_body_is_returned_byte_for_byte` |
| I2 | 재사용이 허용되지 않은 응답은 두 번째 요청에서도 원본에 도달한다 | `test_private_cookie_unmarked_large_are_not_cached` |
| I3 | 요청 쪽에 인증·쿠키·조건부 헤더가 있으면 캐시를 건너뛴다 | `test_auth_and_cookie_requests_bypass_existing_cache` |
| I4 | 끊긴 본문은 저장되지 않는다 | `test_broken_origin_is_not_cached` |
| I5 | 용량을 넘기면 가장 오래 안 쓴 항목부터 버린다 | `test_cache_capacity_and_recently_used_entry` |
| I6 | 해석할 수 없는 요청은 원본에 닿기 전에 거절된다 | `test_malformed_requests_are_refused_before_any_origin_contact` |
| I7 | 동시에 들어온 같은 cold 요청도 서로 다른 바이트를 보지 않는다 | `test_concurrent_misses_stay_bounded_and_agree` |

테스트 단언만으로는 절반만 증명되기 때문이다.

## 1. 동시성 — 고정 worker 풀 + 유한 queue

**고른 것.** 시작할 때 worker 를 `PROXY_WORKERS`(기본 8)개 만들어 두고,
main 스레드는 `accept` 한 소켓 디스크립터를 크기 32의 원형 queue 에 넣기만
한다(`proxy.c:633-653`). worker 는 조건 변수로 꺼내 처리한다.
queue 가 가득 차면 **새 연결을 받아서 즉시 닫는다.**

**버린 대안 (a) 연결마다 스레드 생성.** CS:APP 과제 골격이 유도하는 방식이고
코드는 더 짧다. 버린 이유는 상한이 없다는 것 하나다. 느린 원본 하나가
클라이언트를 붙잡으면 스레드 수가 클라이언트 수를 따라 올라가고, 메모리와
디스크립터가 같이 올라간다. 지금 구조에서는 프록시가 동시에 쥐는 디스크립터가
`1(listen) + 32(queue) + worker 수`로 산술적으로 묶인다 — 실제로 디스크립터
한도를 48로 낮춰도 `accept` 가 EMFILE 을 보지 못한다(24로 낮춰야 본다).
상한을 정하는 것이 이 프로그램에서 배우려던 것이므로, 코드가 짧아지는 쪽을 버렸다.

**버린 대안 (b) 단일 스레드 이벤트 루프(`poll`/`kqueue`).** 이 워크로드에는
이쪽이 더 맞다. 연결 대부분이 I/O 대기이고 CPU 일은 헤더 파싱뿐이니, 스레드
8개로 나눌 이유가 원래 없다. 버린 이유는 비용이 다른 데 있어서다. 이벤트
루프로 가면 요청·응답 파서를 **상태 기계로 다시 써야 한다**(지금은
`rio_readlineb` 로 한 줄씩 블로킹해서 읽는 직선 코드다). 그 재작성은
프록시 본체보다 크고, 이 저장소가 증명하려는 캐시 정확성과는 관계가 없다.
대신 **그 선택의 대가를 측정해서 적어 두는 쪽**을 골랐다: 200 ms 원본에
동시 32 요청을 보내면 worker 8개가 4배치로 처리해 0.820 초가 걸린다
(풀이 병목일 때의 이론값 0.800 초). 이벤트 루프였다면 0.2 초대다.

**대가.** 위 숫자가 그대로 한계다. 느린 원본이 worker 를 점유하면 뒤의
요청은 줄을 선다. 그래서 timeout 에 상한을 두었다(아래 3번).

## 2. 캐시 자료구조 — 16슬롯 배열 + 논리 시계

**고른 것.** `cache_entry cache[16]` 고정 배열에 단조 증가하는 `stamp`
(논리 시계)를 둔다. 조회·저장할 때 `stamp` 를 올리고, 자리나 바이트 한도를
넘으면 `stamp` 가 가장 작은 항목을 버린다(`proxy.c:215-298`). 전체를 mutex
하나로 보호한다.

**버린 대안 (a) 해시 테이블 + 침입형 이중 연결 리스트.** 교과서적인 LRU 다.
O(1) 조회와 O(1) 갱신을 준다. 버린 이유는 항목이 16개라서다. 선형 탐색
16회는 캐시 라인 몇 개를 읽는 일이고, 측정된 HIT 경로 p50 은 0.06 ms 인데
그 안에서 탐색이 차지하는 몫은 소켓 한 번 쓰는 비용에 묻힌다. 반대로 연결
리스트는 포인터 네 개를 항상 맞게 유지해야 하고, 그 불변식이 깨져도 테스트가
아니라 크래시로 드러난다. **항목 수가 늘어나면 이 결정은 뒤집혀야 한다** —
그때가 바뀌는 지점이라는 것까지가 결정의 일부다.

**버린 대안 (b) 항목별 락 또는 읽기-쓰기 락.** 전역 mutex 는 명백한 직렬화
지점이다. 버린 이유는 임계 구역이 이미 짧기 때문이다. HIT 경로는 락 안에서
**데이터를 복사하기만 하고, 락을 푼 뒤에 전송한다**(`proxy.c:235-250`) —
느린 클라이언트가 캐시 전체를 잠그는 일이 없다. 전송을 락 밖으로 뺀 이 한 줄이
락 분할로 얻을 것의 대부분을 이미 가져간다. TSan 아래에서 12개 테스트가
경합 보고 없이 통과하는 것이 지금 설계의 근거다.

## 3. 시간 — connect 전체 deadline 과 유휴 timeout 을 나눈다

**고른 것.** TCP 연결에는 **전체 deadline** 을 건다. `getaddrinfo` 가 돌려준
주소 후보를 순회하되, 각 후보는 "남은 시간"만큼만 기다린다
(`proxy.c:88-129`). 연결이 서면 그 다음부터는 `SO_RCVTIMEO`/`SO_SNDTIMEO`
**유휴 timeout** 으로 바꾼다.

왜 나눴는가. 이 둘은 다른 것을 막는다. deadline 은 "AAAA 가 죽어 있고 A 는
살아 있는" 호스트에서 후보마다 timeout 을 새로 쓰며 시간이 배수로 늘어나는
것을 막는다. 유휴 timeout 은 "한 바이트씩 아주 천천히 보내는" 원본을 막는다.
한쪽만 쓰면 다른 쪽이 뚫린다.

**한계(명시).** DNS 조회 자체는 deadline 밖이고, 전체 다운로드 시간의 상한도
아니다. 큰 응답을 꾸준히 보내는 원본은 유휴 timeout 을 계속 리셋시킬 수 있다.

## 4. 캐시 정책 — 모르는 것은 캐시하지 않는다

**고른 것.** 허용 목록 방식이다. 저장하려면 상태 200, `Content-Length` 가
명확, `Cache-Control: public` 과 `max-age` 가 있고, `max-age > Age`,
`max-age <= 86400`, 본문이 끝까지 도착해야 한다(`proxy.c:527-567`).
`Cache-Control` 안에 **모르는 지시어가 하나라도 있으면 캐시하지 않는다**
(`proxy.c:506-508`). 요청 쪽 `Authorization`·`Cookie`·`Range`·`If-*` 와
응답 쪽 `Set-Cookie`·`Vary`·`WWW-Authenticate` 도 캐시를 끈다.

**버린 대안 (a) RFC 9111 을 제대로 구현.** `no-cache`/`must-revalidate`/
`s-maxage`/`Expires`/휴리스틱 신선도까지. 버린 이유는 범위다. 정확성의 무게
중심이 "얼마나 많은 지시어를 아는가"로 옮겨가는데, 이 저장소가 증명하려는
것은 "모를 때 안전한 쪽으로 넘어지는가"다. 지시어를 반쯤 아는 캐시가 아무것도
모르는 캐시보다 위험하다.

**버린 대안 (b) `ETag`/`If-None-Match` 재검증.** 만료된 항목을 버리는 대신
304 를 받아 되살리는 것. 원본 부하를 크게 줄이는 정석이다. 버린 이유는 이게
**새 기능**이고, 넣는 순간 "조건부 요청 → 304 → 저장된 헤더 병합"이라는
새 상태와 새 실패 모드가 생기기 때문이다. 지금 없다는 것을 README 와 여기에
적어 두는 쪽을 골랐다.

**대가와 관측된 값.** 보수적인 만큼 캐시 적중 기회를 놓친다. 그리고 요청
병합이 없어서, 같은 cold URL 에 동시 요청이 몰리면 원본은 **worker 수만큼**
중복 요청을 받는다(동시 16요청 → 원본 최대 4회, worker 4 기준).
`test_concurrent_misses_stay_bounded_and_agree` 가 이 동작을 고정해 둔다.

## 6. 남은 참고

- `414 URI Too Long`(`proxy.c:380-382`, `proxy.c:396-402`)은 현재 한도에서는
  도달하지 않는다. 요청 라인이 `MAXLINE`(8192)을 넘으면 `header_line` 이
  먼저 거절하므로 캐시 키는 8192 를 넘을 수 없다. 그래도 분기를 남긴 것은,
  `snprintf` 의 반환값을 길이로 그대로 쓰는 자리가 두 곳 있어서다. 한도가
  바뀌면 잘림이 곧 버퍼 과다 읽기가 된다.
- 헤더 이름은 전달할 때 소문자로 정규화한다. HTTP 헤더 이름은 대소문자를
  구분하지 않으므로 의미는 같지만, 응답 바이트가 원본과 다르다는 뜻이다.
